# JS Runtime & Async — Homework

Маленькое приложение на чистом HTML/CSS/JS (без фреймворков), практика closures,
call stack, промисов, async/await и event loop.

Открыть просто `index.html` в браузере, ничего ставить не надо.

## Как замыкание прячет счётчик задачи

В `createTask(name)` переменные `status` и `count` объявлены через `let` прямо
внутри функции. Наружу возвращается объект с функциями `run/getCount/getStatus/reset`,
и только эти функции могут читать или менять `count` — потому что они были
созданы внутри той же функции и "запомнили" доступ к её переменным. Это и есть
замыкание (closure).

Так как `createTask()` вызывается три раза (для Load Users / Load Posts / Load
Comments), каждый раз создаётся новая пара `status`/`count` — они не связаны
между собой, у каждой задачи свой собственный счётчик.

## Как работает call stack на примере из приложения

Когда жмёшь кнопку Run у задачи:

1. Обработчик клика попадает в call stack.
2. Внутри вызывается `task.run()` — тоже добавляется в стек.
3. Внутри `run()` вызывается `setTimeout(...)` — эта функция просто регистрирует
   таймер у браузера и сразу же убирается из стека (она не "спит" в стеке).
4. `run()` возвращает Promise и тоже убирается из стека.
5. Стек пустой — браузер свободен, можно нажимать другие кнопки, пока идёт "загрузка".
6. Когда время таймера истекло, callback из setTimeout попадает в стек отдельным
   заходом (уже после того как event loop его туда переложит) и там выполняется.

## Почему JS не "зависает" пока ждёт setTimeout

`setTimeout` — это не часть самого JS-движка, а API браузера. Вызов
`setTimeout(fn, time)` просто отдаёт браузеру функцию и время, и сразу
возвращает управление — стек не блокируется. Браузер сам отсчитывает время
где-то "снаружи" JS. Когда время вышло, `fn` не выполняется сразу — она
становится в очередь задач (task queue), и event loop положит её в стек только
когда стек будет пустой. Поэтому пока задача "грузится", страница не виснет.

## Мой прогноз vs реальный результат (Event Loop Demo)

Прогноз (записан до запуска, есть и на странице):

```
1 - start
2 - async before await
3 - end (sync)
4 - promise 1 (microtask)
5 - async after await (microtask)
6 - promise 2 (microtask)
7 - timeout 1 (macrotask)
8 - timeout 2 (macrotask)
```

Реальный вывод при запуске полностью совпал с прогнозом.

**Почему так:** сначала весь синхронный код выполняется подряд, без пауз —
это call stack: `1 - start`, потом вызывается `demo()`, там `2 - async before
await` тоже синхронный (до await всё выполняется как обычная функция), потом
`3 - end`. За это время два `setTimeout` и два `Promise.then` просто
"зарегистрировались" — один пошёл в task queue (макротаски), другой в
microtask queue.

Когда синхронный код закончился и стек опустел, event loop сначала полностью
разбирает microtask queue (промисы и код после await) — поэтому `4`, `5`, `6`
выходят раньше, чем таймеры. И только когда микрозадачи закончились, event
loop берёт из task queue первый таймер `7`, потом следующий `8`.

Порядок вкратце: **Call Stack (синхронный код) → Microtask Queue (промисы,
await) → Task Queue (таймеры) → и так по кругу через Event Loop.**

## Разница между task и microtask

- **Microtask** — колбэки промисов (`.then`), код после `await`. Движок
  выполняет ВСЮ очередь микротасков целиком, прежде чем взяться за что-то ещё.
- **Task (macrotask)** — `setTimeout`, события DOM и т.д. Из этой очереди
  event loop берёт только одну задачу за раз, и только когда очередь
  микротасков полностью пуста.

Именно поэтому в демке оба промиса и продолжение async-функции (4, 5, 6)
выполняются раньше обоих таймеров (7, 8), хотя первый таймер был поставлен в
очередь раньше, чем второй промис.

## Как обрабатываю несколько промисов и ошибки

- У одной задачи: `task.run().then(...).catch(...)` — если промис упал,
  ошибка ловится в `.catch`, а не роняет всё приложение.
- Для "Run All Tasks" использую `Promise.allSettled`, а не `Promise.all`.
  `Promise.all` остановился бы на первой же упавшей задаче и не дождался бы
  остальных, а `allSettled` ждёт вообще всех — и успешных, и упавших — и
  только тогда можно честно написать "All tasks finished".
- В Sequential-сравнении каждый `await` обёрнут в свой `try/catch`, чтобы
  ошибка одной задачи не остановила выполнение следующих.

## Разница между sequential и concurrent

```js
await t1.run();
await t2.run();
await t3.run();
```
Тут вторая задача даже не стартует, пока не закончится первая — время
складывается: 800 + 1200 + 600 ≈ 2600ms.

```js
await Promise.allSettled([t1.run(), t2.run(), t3.run()]);
```
Тут все три `run()` вызываются сразу, все три таймера стартуют одновременно —
ждём только самую долгую из них, около 1200ms.

Разницу видно прямо в кнопках Run Sequential / Run Concurrent на странице —
concurrent почти в 2 раза быстрее на этих же трёх задачах.
