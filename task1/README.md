
### Как замыкание прячет счётчик задачи

В `createTask(name)` переменные `status` и `count` создаются внутри самой функции. Потом наружу возвращается объект с функциями `run`, `getCount`, `getStatus` и `reset`.

Эти функции всё равно имеют доступ к `status` и `count`, хотя `createTask` уже закончила работу. Это происходит благодаря замыканию (closure) — функции как бы запоминают переменные из своего окружения.

`createTask()` вызывается три раза для разных задач: Load Users, Load Posts и Load Comments. При каждом вызове создаются свои `status` и `count`, поэтому счётчики у задач независимые.

### Как работает call stack

Когда я нажимаю кнопку `Run`, сначала в call stack попадает обработчик события клика. Внутри него вызывается `task.run()`, поэтому эта функция тоже попадает в стек.

В `run()` вызывается `setTimeout()`. Он не заставляет JavaScript ждать. Браузер просто получает таймер и callback, а `run()` продолжает выполняться и возвращает Promise.

После этого стек становится пустым. Поэтому браузер может спокойно обрабатывать другие события, пока таймер ещё работает.

Когда таймер заканчивается, его callback попадает в очередь задач. Потом event loop, когда стек свободен, переносит его в call stack и callback выполняется.

### Почему JS не зависает из-за setTimeout

`setTimeout()` не блокирует JavaScript. Таймером занимается браузер, а не call stack самого JavaScript.

То есть JS не сидит и не ждёт эти 800 или 1200 миллисекунд. Он передаёт callback браузеру и может заниматься другими делами.

Когда время заканчивается, callback сначала попадает в очередь задач. Он выполнится только тогда, когда call stack освободится.

### Event Loop Demo

Перед запуском я предположил такой порядок:

1. start  
2. async before await  
3. end (sync)  
4. promise 1  
5. async after await  
6. promise 2  
7. timeout 1  
8. timeout 2  

После запуска результат оказался таким же.

Сначала выполняется весь обычный синхронный код. Поэтому сначала идут `start`, `async before await` и `end`.

`Promise.then()` и продолжение функции после `await` попадают в microtask queue. Таймеры из `setTimeout()` идут в task queue.

Когда синхронный код заканчивается, event loop сначала разбирает microtask queue. Поэтому `promise 1`, `async after await` и `promise 2` выполняются раньше таймеров.

И только после этого начинают выполняться callbacks из `setTimeout()`.

Если совсем коротко, получается:

**Call Stack → Microtask Queue → Task Queue → Event Loop**

### Task и Microtask

Microtask — это, например, `.then()` у Promise и продолжение `async`-функции после `await`.

Task (или macrotask) — это, например, `setTimeout()` и события DOM.

Главный момент в том, что после выполнения синхронного кода JavaScript сначала очищает очередь microtask. Поэтому промисы выполняются раньше таймеров.

В моей демке именно поэтому оба Promise и код после `await` идут раньше двух `setTimeout`, даже несмотря на порядок, в котором они были написаны.

### Как обрабатываются несколько Promise и ошибки

Для отдельной задачи используется:

`task.run().then(...).catch(...)`

Если задача завершилась ошибкой, она попадает в `.catch()`, поэтому ошибка не ломает всё приложение.

Для кнопки `Run All Tasks` используется `Promise.allSettled()`. Я выбрал его потому, что здесь нужно дождаться окончания всех задач, даже если какая-то из них завершится ошибкой.

Если использовать `Promise.all()`, то при первой ошибке общий Promise сразу перейдёт в состояние rejected.

В последовательном запуске каждая задача дополнительно находится в своём `try/catch`. Поэтому если одна задача упадёт, следующие всё равно смогут запуститься.

### Sequential и Concurrent

При последовательном запуске:

```js
await t1.run();
await t2.run();
await t3.run();
```

сначала полностью выполняется первая задача, потом начинается вторая, и только после неё третья.

Поэтому время примерно складывается:

**800 + 1200 + 600 = 2600 ms**

При concurrent-запуске:

```js
await Promise.allSettled([
    t1.run(),
    t2.run(),
    t3.run()
]);
```

все три задачи запускаются сразу. Поэтому ждать приходится примерно столько, сколько занимает самая длинная задача — около **1200 ms**.

Из-за этого `Run Concurrent` работает заметно быстрее, чем `Run Sequential`.
